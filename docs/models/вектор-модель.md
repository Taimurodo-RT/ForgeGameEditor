## Три части и их границы

```
                    engine/vector  (новый, без рисования)
                    пути, чтение SVG-пути, морфинг, ease
                     │                 │                  │
     ┌───────────────┘                 │                  └──────────────────┐
     ▼                                 ▼                                     ▼
 «Пиксельные» (только редактор)    интерфейс (engine/ui)                  игра (Luau)
 ThorVG + поза на Luau             lunasvg под реальный размер            морфинг SVG на экранах игры
 запекание → картинка и клипы      живой SVG: части, морфинг             через тот же engine/vector
     │
     ▼
 обычная картинка «Ресурсов» + анимации шаблона  ──►  игра играет их как сейчас, без ThorVG
```

- **ThorVG** связан только с редактором, с режимом «Пиксельные» (решение Романа). Игра, пакет и модули его не
  подключают.
- **lunasvg** остаётся единственным движком SVG интерфейса редактора и игр (решение Романа).
- **Морфинг** живёт в `engine/vector` и ни от одного движка рисования не зависит (решение Романа: доступен интерфейсу
  и игровым сценариям; устройство модуля — предложение). Модуль отдаёт точки, а рисует их тот, кому они нужны.

## Часть 1. «Пиксельные» на ThorVG

### Что делает автор (предложение)

- Во вкладке «Анимация» выбирает режим «Пиксельные» (сейчас кнопка `an-mode-pixel` с пометкой «появится»,
  `ui/editor/editor.rml:1181`).
- **Слева** — векторные анимации игры: имя, размер кадра, число клипов.
- **В середине** — два просмотра рядом:
  - вектор крупно, живой, рисует ThorVG;
  - пиксельный кадр в итоговом размере и увеличенный без сглаживания, то есть ровно то, что будет запечено.
  - Под ними шкала времени клипа. Пробел, ← и → работают как в «Покадровой». Калька соседних кадров включается
    отдельно.
- **Справа**:
  - части персонажа деревом, как они вложены в SVG; выбранная часть подсвечена, её опорная точка перетаскивается
    мышью;
  - параметры скрипта полями (скорость, длина шага и что объявит скрипт) и seed;
  - клипы: имя состояния, число кадров, кадров в секунду из того же списка, что в «Покадровой», повтор;
  - запекание: размер кадра, палитра, контур.
- Скрипт открывается во внешнем редакторе или в поле вкладки; при сохранении файла просмотр обновляется сам.
- «Запечь» пишет картинку в «Ресурсы». «Отдать шаблону…» ставит её выбранному шаблону и пишет его анимации.
  Каждое из этих действий — один шаг Ctrl+Z / Ctrl+Y.

### Исходник (предложение)

Три файла в «Ресурсах» игры с одним именем:

| Файл | Что в нём |
|---|---|
| `Герой.svg` | рисунок. Части — группы и фигуры с `id` (`arm_l`, `leg_r`, `head`). Обычный SVG из любого редактора, без своих атрибутов. |
| `Герой.luau` | скрипт позы (ниже). |
| `Герой.pixel.json` | всё остальное: ссылка на SVG и скрипт, опорные точки частей, размер кадра, seed, значения параметров, клипы, настройки запекания и id запечённой картинки. |

```json
{
  "svg": "<Guid ресурса Герой.svg>",
  "script": "Герой.luau",
  "frame": [32, 32],
  "seed": 1234,
  "params": {"speed": 1.0, "step": 6},
  "pivots": {"leg_l": [29.5, 41], "leg_r": [34.5, 41], "arm_l": [25, 28], "arm_r": [39, 28], "head": [32, 26]},
  "clips": {
    "stand": {"frames": 4, "fps": 6, "loop": true},
    "walk": {"frames": 8, "fps": 12, "loop": true}
  },
  "bake": {"palette": "svg", "outline": null, "picture": "<Guid запечённой картинки>"}
}
```

- Опорные точки лежат в `.pixel.json`, а не в SVG. Тогда SVG остаётся обычным файлом, а одну иерархию частей сможет
  читать и «Скелетная» (вопрос 3).
- Игра эти три файла не читает и в папку игры их не копирует. В игру попадает только запечённая картинка, через
  `sources.json`, как любая картинка «Ресурсов».

### Скрипт позы (предложение)

Скрипт выполняется в той же песочнице Luau, что и скрипты игры (`engine/script`: без `io`, `os`, загрузки файлов,
с бюджетом времени на вызов), но в отдельной среде редактора, а не в игре.

```lua
return {
  params = { speed = 1.0, step = 6 },          -- поля справа во вкладке
  pose = function(t, p, rng)                    -- t — секунды от начала клипа
    local s = math.sin(t * p.speed * 2 * math.pi)
    part("leg_l"):set{ rot = 28 * s }
    part("leg_r"):set{ rot = -28 * s }
    part("upper"):set{ y = -1.5 * math.abs(s) }
    shape("mouth"):morph("mouth_open", ease.inOut(0.5 + 0.5 * s))
  end,
}
```

- **Поза — чистая функция времени** (вопрос 4). Любой кадр считается сразу, без проигрывания прошлых. Поэтому работают
  перемотка, калька и запекание кадра k в момент `t = k / fps`. Часов компьютера скрипт не видит.
- **Случайность** — только `rng`, генератор с seed из `.pixel.json`, заново засеянный на каждый кадр. Общий
  `forge.random` хоста (`engine/script/src/api_core.cpp:263`) здесь не годится: он один на весь хост.
- `part(id):set{x, y, rot, scale, opacity, fill}` — сдвиг, поворот вокруг опорной точки, масштаб, прозрачность и цвет
  части. Поворот и масштаб считаются вокруг опорной точки из `.pixel.json`. Вложенные части наследуют движение
  родителя, как группы в SVG.
- `shape(id):morph(цель, k)` — морфинг фигуры в другую фигуру того же SVG (например, спрятанную) через
  `engine/vector`, k от 0 до 1. Это тот же морфинг, что получат интерфейс и игра (часть 3).
- `ease.*` — набор функций сглаживания движения, общий с `engine/vector`.
- Ошибка в скрипте показывается строкой и номером, просмотр стоит на последней удачной позе.

### Как рисует ThorVG

- ThorVG загружает SVG один раз. Части находятся по `id` (`Picture::paint(Accessor::id(...))`), поза меняет только их
  матрицы, прозрачность и цвет. Морфинг заменяет путь фигуры точками из `engine/vector`.
- Две особенности, найденные на стенде, обходятся сразу:
  - после правки частей картинку надо пометить изменённой (`pic->transform(pic->transform())`), иначе ThorVG её не
    перерисует;
  - второй экземпляр того же файла, загруженный по пути, теряет `id` частей (общий кэш загрузчика). Каждый экземпляр
    грузится из памяти с `copy = true`.
- Замеры стенда для ориентира (облако, 4 ядра): поза 6 частей — 0.15 мс на кадр 64 px и 0.39 мс на 256 px в один
  поток; морфинг 400 фигур на 512 px — 2.9 мс в один поток и 1.8 мс в три. Для живого просмотра в редакторе это с
  большим запасом.

### Запекание (предложение)

На стенде чисто вышел только один способ, его и берём:

1. Каждая фигура рисуется отдельно, заливка и обводка — отдельными проходами, со сглаживанием.
2. Пиксель получает **точный цвет** этой заливки или обводки, если она покрывает его хотя бы наполовину. Фигуры
   ложатся друг на друга в порядке SVG.
3. Полупрозрачных пикселей и чужих цветов не бывает. Площадь фигуры отличается от точной меньше чем на 1%
   (на стенде −0.6%). Время — 0.9 мс на кадр 32×32 с 10 фигурами.
4. Палитра: по умолчанию цвета самого SVG. Можно привязать к «Цветам игры» (вопрос 5).
5. Контур в 1 пиксель по желанию — тем же правилом, что эффект `Outline` вкладки «Изображения»
   (`engine/assets/include/forge/assets/image_edit.h:97`).
6. Сдвиг корня округляется до целого пикселя, чтобы фигура не дрожала между кадрами.

Чего не делаем: встроенный режим ThorVG `EngineOption::Aliased` закрашивает любой задетый пиксель, фигура на стенде
потолстела на 17%, контуры съели лицо. Порог по готовой картинке даёт чужие цвета на стыках. Детали меньше пикселя
пропадают при любом способе: их рисуют с запасом, и вкладка предупреждает о частях, которые в итоговом размере уже
пикселя.

### Что получает конструктор

- **Картинка**: обычная PNG-картинка «Ресурсов», полоса кадров всех клипов подряд. В её `.meta` записано, из какой
  `.pixel.json` она запечена. Повторное запекание пишет новый вариант того же ресурса, копии в играх догоняют через
  `sources.json` и F5, как после Ctrl+S во «Изображениях».
- **Анимации шаблона**: «Отдать шаблону…» ставит шаблону картинку, «Кадров в картинке» и `animations` по клипам. Это
  те же поля, что пишет «Покадровая» (`Template::animations`, `Clip`). Состояния берутся из модуля игры
  (`LevelModule::anim_states`, `engine/level/include/forge/level/level.h:306`).
- Дальше игра и редактор работают с ними как с любой картинкой и анимацией. «Покадровая» может поправить клип,
  «Изображения» — пиксели. Если запечённую картинку правили руками, повторное запекание предупреждает, что правки
  пропадут.
- **Лимиты.** Когда модель писалась, в полосе было не больше 8 кадров (`kMaxFrames`), в клипе не больше 16
  (`kMaxClipFrames`, `engine/objects/include/forge/objects/library.h`), и персонаж с «Стоит» на 4 кадра и «Идёт» на 8
  уже не помещался. По решению Романа (вопрос 2) на шаге 2 оба лимита подняты до 32.

### ThorVG в сборке (предложение)

- Подключается одной библиотекой, которую линкует только `forge_editor`. Проверка в CI: ни одна цель игры, пакета и
  модулей от неё не зависит.
- В ThorVG 1.1 нет сборки CMake, только meson. Своя цель CMake со списком исходников: процессорный движок, загрузчик
  SVG, свой `config.h`. Потоки ThorVG включены, OpenMP выключен. Загрузчик Lottie пока не нужен; если понадобится,
  выражения Lottie (встроенный JavaScript) остаются выключенными.
- Лицензия MIT.
- SVG персонажа проверяется при выборе: то, что ThorVG не рисует (маркеры, обрезка с правилом `evenodd`, вложенный
  `<svg>`, цвета `#RGBA`, `#RRGGBBAA`, `hsla`, фильтры кроме размытия; по стенду), называется строкой с элементом, а не
  молча рисуется иначе.

## Часть 2. lunasvg в интерфейсе

Цель — чёткий интерфейс редактора и игр на любом экране и живые SVG в интерфейсе. Стенд показал, что смена библиотеки
чёткости не прибавит: значки на 16–48 px у обеих одинаковы. Размывают интерфейс два места в Forge.

1. **Масштаб экрана.** Forge не спрашивает систему о масштабе (`SDL_GetWindowDisplayScale` не вызывается), dp-ratio
   редактора всегда 1.0, а все 1 939 значений в `.rcss` написаны в `px`, которые встроенный RmlUi не масштабирует
   (`third_party/rmlui/Source/Core/ComputeProperty.cpp:67, 70`).
   - dp-ratio = масштаб дисплея × «Масштаб интерфейса» игры; смена масштаба при переносе окна
     (`SDL_EVENT_WINDOW_DISPLAY_SCALE_CHANGED`) пересчитывает интерфейс.
   - `px` считается логическим пикселем и умножается на dp-ratio, как в браузере (предложение). Это одна правка
     встроенного RmlUi с пометкой `// Forge:` вместо переписывания 1 939 значений.
2. **SVG под реальный размер.** Сейчас любая SVG рисуется в 128 px по длинной стороне и растягивается
   (`kSvgRasterSize`, `engine/ui/src/gpu_renderer.cpp:613`).
   - SVG растрируется в размер блока элемента × dp-ratio. Разобранный документ хранится, растр кэшируется по документу,
     размеру и цвету. При смене размера старый растр показывается, пока не готов новый.
   - Основа — SVG-плагин RmlUi: он сделан на lunasvg и делает ровно это. Во встроенную копию его не взяли
     (`third_party/rmlui/README.md`); переносим с пометками `// Forge:`. Совместимость плагина 6.3 с lunasvg 3.5
     проверить первым делом.
   - Цвет: значок берёт `color` элемента через `currentColor`, тема меняет цвет без второго файла.
3. **SVG в «Ресурсах».** Импорт `.svg` (сейчас только растр, `engine/assets/src/importers.cpp:56–64`). В игру SVG
   копируется как есть, рисует его lunasvg. При импорте проверяется то, чего lunasvg не рисует (фильтры размытия и
   тени: для них в интерфейсе есть свои `filter` и `box-shadow` RCSS), и называется строкой.
4. **Рамки из девяти частей для SVG.** Углы растрируются в целых пикселях устройства, без швов.
5. **Живой SVG.** Скрипт интерфейса или игры меняет части SVG-элемента по `id`: сдвиг, поворот, цвет, прозрачность,
   морфинг пути (часть 3). Элемент перерисовывается в своём размере на следующем кадре. Стенд: одна фигура обходится
   lunasvg в 0.17 мс на 256 px и 0.6 мс на 512 px. lunasvg после любой правки заново раскладывает весь документ,
   поэтому живыми делаются небольшие SVG: значки, кнопки, индикаторы. Анимированный масштаб квантуется ступенями,
   между ступенями растягивается последний растр.

## Часть 3. Морфинг: общий модуль `engine/vector`

Решение Романа: морфинг должен быть доступен интерфейсу и особым игровым сценариям. Поэтому он не живёт ни в ThorVG,
ни в lunasvg (устройство модуля — предложение).

- **Модель.** Путь — контуры из кубических кривых (`move`, `line`, `cubic`, `close`). Чтение пути из атрибута `d`
  (все команды SVG, дуги и квадратичные кривые переводятся в кубические) и из фигур `rect`, `circle`, `ellipse`,
  `polygon`. Запись обратно в строку `d`.
- **Подготовка пары** (один раз на пару фигур):
  - контуры сопоставляются по порядку, недостающий контур стягивается в точку в центре соседнего;
  - у контуров выравнивается число кривых: длинные кривые делятся, пока числа не сравняются;
  - направление обхода приводится к одному;
  - начальная точка сдвигается так, чтобы точки пар были ближе всего.
- **Смешивание**: точки, цвет заливки и обводки, толщина обводки и прозрачность, k от 0 до 1. `ease.*` — тот же набор,
  что у скриптов позы.
- **Выход**: точки (для ThorVG), строка `d` (для lunasvg), позже треугольники для GPU-слоя векторов, если он появится
  (этап 2 ресёрча).
- **Кто пользуется**:
  - «Пиксельные»: `shape(id):morph(цель, k)` в скрипте позы;
  - интерфейс: морфинг части живого SVG; позже дорожка морфинга в движении по ключам вкладки «Интерфейс»;
  - игра: Luau-функция морфинга части SVG на экране игры. Морфинг объектов прямо в мире игры ждёт GPU-слоя: до него
    — только через растр на процессоре для немногих объектов.

### Шаг 1: модуль `engine/vector` (2026-10-13, ветка `claude/vector-morph`, draft PR #94)

**Что сделано.**

- **Где**: `engine/vector`, библиотека `forge::vector`; зависит только от `forge::core`, ни ThorVG, ни lunasvg не
  знает. Четыре заголовка: `path.h` (пути), `morph.h` (морфинг), `ease.h` (сглаживание), `trig.h` (тригонометрия).
- **Путь**: контуры из кубических кривых (`Contour`: начало, кривые, замкнут ли). Прямые, квадратичные кривые и дуги
  читаются как кубические. Замкнутый контур всегда кончается в своём начале: линия, которую рисует `Z`, — отдельная
  кривая. Иначе при сдвиге начала в морфинге она бы потерялась.
- **Чтение `d`** (`parse_path`): все команды SVG (M L H V C S Q T A Z, абсолютные и относительные) и числа так, как их
  пишет SVG (`1e3`, `-.5`, `1-2` — два числа, `1.5.5` — тоже два, флаги дуги без пробелов). Ошибка останавливает
  чтение на месте, как SVG рисует путь до ошибки: путь до неё остаётся, причина называет номер знака. Пустой `d` — не
  ошибка; одинокий M — не контур.
- **Запись `d`** (`to_d`): M, C и Z; каждое число в самой короткой записи, которая читается обратно в то же число, так
  что «записал — прочитал» даёт тот же путь бит в бит.
- **Фигуры SVG**: `rect` со скруглением, `circle`, `ellipse`, `polyline` (замкнутый — `polygon`) и `parse_points` для
  атрибута `points`. Начинаются и обходятся, как велит SVG 2: круг — с правой точки по часовой стрелке на экране,
  прямоугольник — с верхней стороны после скругления.
- **Морфинг**: `Shape` — путь и вид (`Look`: заливка и обводка цветом sRGB 0…1, как его пишет SVG, со своей
  прозрачностью; толщина обводки; прозрачность всей фигуры). `prepare(a, b)` один раз готовит пару, `mix(пара, k, out)`
  каждый кадр пишет фигуру в `out` и не выделяет память, когда у `out` уже есть нужный размер. `hex()` пишет цвет
  обратно в атрибут SVG.
- **Сглаживание** (`ease`): семь слов вкладки «Интерфейс» — smooth, linear, in, out, back, bounce, elastic — и те же
  кривые, которыми интерфейс двигает слои (твины RmlUi: smooth — кубическая in-out, back, bounce и elastic — out).
  Морфинг, поставленный рядом с движением слоя, идёт с ним в такт. Концы точные: 0 даёт 0, 1 даёт 1; back и elastic
  проскакивают за 1 (до 1,1 и 1,26) и возвращаются.
- **Одинаково на Windows и Linux**: дугам и elastic нужны синус, арктангенс и экспонента, а библиотека C на двух
  системах даёт их с разницей в последнем бите. `trig.h` считает их сам рядами, только четырьмя действиями, корнем и
  округлением, которые IEEE 754 делает одинаково везде. От стандартных отличаются не больше чем на 4e-16.

**Отличия от записанного выше.**

1. Недостающий контур стягивается в центр **своего** контура (того, которого нет у другой стороны), а не «соседнего»:
   дырка исчезает на месте, а не уезжает к соседу.
2. Число кривых выравнивается не делением пополам самой длинной, а раздачей кусков: каждый новый кусок достаётся
   кривой, у которой куски сейчас самые длинные, и кривая режется на равные шаги. Круг из четырёх кривых против звезды
   из десяти режется на 3, 3, 2, 2, и точки идут по кругу почти поровну; деление пополам дало бы 4, 2, 2, 2, и четыре
   луча звезды сбились бы на одну четверть круга.
3. Направление: замкнутые контуры сводятся по знаку площади, как записано. У плоского контура (площадь 0, например
   линия туда и обратно) своего направления нет, и берётся то из двух, при котором пара ближе. Открытые контуры
   сводят ближние концы.
4. Начало подбирается по всем точкам кривых (обе контрольные и конец), а не только по узлам.
5. Цвет, прозрачность и толщина смешиваются при k, удержанном в 0…1, а точки идут и за концы — для back и elastic.
   Выключенная заливка или обводка — цвет другой стороны с прозрачностью 0, поэтому она плавно появляется или гаснет.
   Замкнутость контура переключается на k = 0,5.
6. `ease` — слова вкладки «Интерфейс», а не `inOut` из примера скрипта позы выше: одни слова в обоих местах. В скрипте
   позы (шаг 2) они так и будут называться.
7. Цвет из атрибутов SVG (`#rgb`, имена цветов) этот шаг не читает: его приносит тот, кто читает SVG (ThorVG отдаёт
   цвет числами на шаге 2, интерфейс — на шаге 4).
8. Треугольников для GPU-слоя нет: слоя пока нет.

### Шаг 3: интерфейс, этап 0 (2026-10-14, ветка `claude/ui-scale`)

Роман: «Продолжай» (2026-10-14, 02:25 UTC), после слияния PR #95. «Изображения» остаются на паузе.

**Что сделано.**

- **Масштаб экрана.** `engine/ui` спрашивает систему о масштабе дисплея, на котором окно (`SDL_GetWindowDisplayScale`):
  при запуске, по `SDL_EVENT_WINDOW_DISPLAY_SCALE_CHANGED` и раз в кадр, если приложение это событие не передало.
  dp-ratio = масштаб дисплея × масштаб интерфейса (`Ui::set_scale`). Все контексты получают новый dp-ratio на ходу,
  кроме закреплённых (`Ui::pin_dp_ratio`): страница игры на холсте «Интерфейса» и превью шаблонов показываются в своём
  размере. В игре масштаб интерфейса — настройка «Размер интерфейса» (`ui_scale` в `settings.json`, 50–300 %), в
  редакторе — 1. `--ui-scale S` у редактора и игры подставляет масштаб дисплея (от 0,5 до 4). Самопроверки и снимки
  без него идут при 1, чтобы пиксели были одни на всех машинах. `Ui::stand_in_display_scale` подставляет масштаб
  дисплея на ходу для теста; как и системный, он берётся только по событию окна.
- **`px` — логический пиксель.** Одна правка встроенного RmlUi с пометками `// Forge:` в разборе единиц
  (`PropertyParserNumber`, `TypeConverter`, `CalcExpression`): `px` читается как `dp`, а пиксель окна называется
  `devpx`. Значения в `.rcss` не переписывались. `devpx` пишет C++, который мерит экран и кладёт длину обратно в
  стиль: доки, схема «Логики», «Сюжет», палитра цветов, «Объекты», «Пиксельные», холст «Интерфейса» (линейки, рамки
  выбора, направляющие), длинные списки, связи уровня в slice. Элемент `<lines>` берёт точки в пикселях окна или, с
  `points="px"`, в px стиля; толщина линии всегда в px.
- **SVG в своём размере.** SVG-плагин RmlUi 6.3 перенесён в `third_party/rmlui/Source/SVG`; lunasvg 3.5 подошёл ему без
  правок. Растр делается в размере блока элемента × dp-ratio и ставится на целые пиксели окна, кэш — по документу,
  размеру и цвету. Так рисуются `<img src="….svg">`, `decorator: image(….svg)` (фоны и маски тоже), `decorator:
  svg(…)` и `<svg>` прямо в странице. `GpuRenderer` растрирует SVG в его собственном размере (до 2048 px, раньше всегда
  128) только там, где размер никто не задал, и отдаёт этот размер раскладке.
- **currentColor.** Картинка, в которой написан `currentColor`, рисуется цветом `color` элемента, и смена `color`
  перерисовывает её. Растры такой картинки различаются цветом; у остальных цвет в ключ кэша не входит.
- **Рамки из девяти частей.** `border-image-source: url(рамка.svg)`: картинка растрируется один раз в масштабе угла
  (ширина рамки к срезу), границы всех частей округлены до целых пикселей окна. Углы выходят такими же, как картинка,
  нарисованная сразу в этом размере, а между частями нет швов.
- **SVG в «Ресурсах».** Импортёр `svg` кладёт файл в игру как есть. При импорте файл сверяется с тем, что строит
  lunasvg, а то, чего она не нарисует, называется одной строкой в журнале редактора и в строке «В игре» под просмотром:
  - фильтры, со словами, что они делают (размытие, тень, сдвиг, смена цветов, заливка, наложение);
  - анимация SVG; неизвестные элементы, с припиской «и всё внутри тоже», если внутри что-то есть;
  - текст: lunasvg рисует его шрифтом компьютера игрока, надёжнее перевести в кривые;
  - `<image>` не из `data:`, CSS `filter`, `mix-blend-mode`.

  Если есть фильтр, строка заканчивается тем, что размытие и тень интерфейсу дают свойства `filter` и `box-shadow`
  RCSS. Элементы редакторов (`inkscape:`, `sodipodi:`), `title`, `desc` и `metadata` не называются. Файл, который
  lunasvg не читает, назван так. Просмотр и значок в списке рисует lunasvg.
- **«Интерфейс» берёт картинку из «Ресурсов».** В списке картинки слоя после картинок игры стоят «имя — из «Ресурсов»»
  (PNG, JPG, TGA, SVG). Выбор копирует файл в `pictures/` игры как есть и записывает связь в `sources.json`. `Sources`
  принимает в `pictures` SVG, который читает lunasvg.
- Чтение SVG «как написан» переехало из `forge::pixel` в `engine/vector` (`forge/vector/svg.h`), у элемента появился
  префикс пространства имён. Им пользуются «Пиксельные» и «Ресурсы», «Ресурсам» ThorVG не нужен.

**Отличия от записанного выше.**

1. «Масштаб интерфейса» игры — бывшая настройка «Размер интерфейса». Раньше она меняла только длины в `dp`, теперь
   растёт вся оболочка игры: меню, настройки, сохранения. Своей настройки масштаба у редактора пока нет, его dp-ratio
   — масштаб дисплея.
2. Экраны автора из «Интерфейса» вписываются в окно в px и при любом масштабе занимают ту же часть экрана, как записано
   в `docs/ui-editor.md`: игра встречает экраны пикселями окна.
3. «Старый растр показывается, пока не готов новый» не сделано: растр делается сразу, в кадре, где сменился размер. Для
   значков это доли миллисекунды (стенд: фигура 0,17 мс на 256 px).
4. Появилась единица `devpx`, которой в модели не было. Без неё C++, который кладёт в стиль измеренные пиксели окна,
   при dp-ratio 2 сдвигал бы всё вдвое.

**Известные пределы этой версии.**

- Вид уровня и холст «Интерфейса» считают в пикселях окна. При 2.0 мир на уровне выглядит мельче, а масштаб холста
  100 % — это пиксель страницы на пиксель окна.
- Эффекты шрифта (`font-effect`) и сдвиги плитки в декораторах остаются в пикселях окна.
- Значки (48 px) и просмотр (256 px) «Ресурсов» растрируются в постоянном размере и при 2.0 растягиваются.
- Отступ `body` у страницы, написанной рукой, растёт с масштабом и вписыванием не учитывается: при 150 % такая страница
  сдвигается на несколько пикселей. Страницы, которые пишет редактор, его обнуляют.
- Экран автора вписывается в окно преобразованием (`transform`) корня страницы. SVG на нём растрируется в размере
  страницы, а потом масштабируется вместе с ней. В окне размера экрана (1920 × 1080 у шаблонов) картинка пиксель в
  пиксель, в окне другого размера она слегка мягче. Растр с учётом этого масштаба — работа следующего этапа (сделано в шаге 4).
- Перенос окна на настоящий дисплей другого масштаба автоматически не проверяется: на машинах CI один дисплей.
  Самопроверки подставляют масштаб дисплея и шлют событие окна тем же путём, каким его передаёт приложение. Что
  система при переносе шлёт `SDL_EVENT_WINDOW_DISPLAY_SCALE_CHANGED` и отдаёт новый `SDL_GetWindowDisplayScale`,
  остаётся ручной проверкой.
- Мышью при 1, 1,5 и 2 проверены холст «Интерфейса» и длинный список «Ресурсов». Схемы «Логики» и «Сюжета», вид

  рабочее дерево не тронуто), `ui-scale` упал так же. После исправления `ui-scale` прошёл с `\r\n` (6 файлов экранов C
  приведены) и с `\n` (0). Без приведения новая проверка падает первой: «hud.json and hud.html byte for byte as the
  editor writes the HUD it opened».

### Шаг 4: живой SVG и морфинг в интерфейсе и в Luau игры (2026-10-14, ветка `claude/vector-live`)

Поручение передано через Codex от Романа (2026-10-14, 07:26 UTC): после приёмки PR #96 и исправления фикстур Windows
(PR #97) готовить шаг 4 в тех же границах, новые PR не сливать.

**Что сделано.**

- **Живой элемент в SVG-плагине RmlUi** (`RmlUi/SVG/LivePicture.h`, правки с пометкой `// Forge:`). Живой элемент рисует
  свои SVG-картинки из собственных документов lunasvg, прочитанных из тех же файлов: `<img>`, `<svg>`, `decorator:
  image(…svg)` и `svg(…)`, маски, `border-image`. Документ меняет функция `apply`: при создании и после каждого `Touch`.
  На следующем кадре элемент рисуется заново в своём размере, остальные элементы с этим файлом рисуют общий растр.
- **Части картинки по `id`** (`forge/ui/live_svg.h` в `engine/ui`): `svg_move`, `svg_turn`, `svg_color`, `svg_fade`,
  `svg_morph`, `svg_reset`.
  - Каждое изменение считается от файла, а не от прошлого изменения: два `move(10, 0)` оставляют часть на 10 правее.
    Изменение держится до `reset`.
  - Поворот идёт вокруг центра части, как её рисует файл. Цвет ложится на часть и на фигуры внутри неё со своей
    заливкой.
  - Морфинг берётся из `forge::vector` (часть 3): контур `<path>` идёт к другой фигуре того же файла, k от 0 до 1. Пара
    готовится один раз на файл. Заливка, обводка, её толщина и прозрачность смешиваются, если у обеих фигур простой
    цвет; градиент и `currentColor` остаются как в файле.
  - Если изменение не применилось (части нет, морфинг не в `<path>`, у фигур разные `transform`), об этом одна строка
    по-русски, один раз (`svg_problems`).
- **Фигуры SVG для морфинга** (`forge/vector/svg_shape.h`) переехали из «Пиксельных» в `engine/vector`: контур элемента,
  наследуемые свойства, цепочка `transform`. Ими пользуются и «Пиксельные», и живой SVG.
- **Игра.**
  - В Luau: `forge.ui.svg_move(экран, слой, часть, x, y)`, `svg_turn(…, градусы)`, `svg_color(…, "#rrggbb")`,
    `svg_fade(…, 0…1)`, `svg_morph(экран, слой, часть, в_фигуру, k)`, `svg_reset(экран, слой)`.
  - `forge.ease(как, t)` — тот же набор, что у скриптов позы: `smooth`, `linear`, `in`, `out`, `back`, `bounce`,
    `elastic`.
  - Слой ищется по имени из «Интерфейса» или по id. Изменение получают все слои с этим именем, клетки списков тоже
    (`GameScreens::svg`).
  - Те же действия есть нодами в палитре «Логики»: «Сдвинуть часть картинки», «Повернуть часть картинки», «Цвет части
    картинки», «Прозрачность части картинки», «Морфинг части картинки», «Картинка слоя как в файле» (категория «Экраны»)
    и «Плавность» («Математика»).
  - Если экрана или слоя нет или цвет не читается, это ошибка скрипта в его строке. Если в файле нет части, это строка
    в журнале игры.
- **Растр под преобразованиями** (`RmlUi/Core/PictureScale.h`). SVG растрируется в масштабе `transform` элемента и
  его предков, по длинной из двух осей: поворот растр не меняет.
  - Масштаб, который держится, берётся как есть.
  - Меняющийся масштаб (анимация) идёт ступенями 2^(1/4) вверх. Между ступенями растягивается последний растр (это
    пункт 5 части 2). Продержавшись 8 кадров, масштаб даёт растр точно в нём.
  - Так рисуются все виды SVG-картинок. Кэш отличает размер растра от размера на странице.
  - Предел шага 3 закрыт: экран автора, вписанный в окно другого размера, растрирован в пикселях окна.

**Отличия от записанного выше.**

1. Своих скриптов у страниц «Интерфейса» нет. Интерфейс получает живой SVG через `forge/ui/live_svg.h` (C++), экраны
   игры — через Luau и ноды «Логики». Дорожка морфинга в движении по ключам вкладки «Интерфейс» остаётся на потом, как
   и записано в части 3.
2. Ступени масштаба идут от 1/8 до 8, сторона растра не больше 4096 px. Перспектива и 3D-повороты не учитываются:
   масштаб берётся из осей x и y матрицы.

**Известные пределы этой версии.**

- Живое состояние картинки не пишется в сохранение и пропадает при перезагрузке страницы экрана. Картинка снова
  становится файлом, пока скрипт не скажет изменение снова, например «Каждый шаг».
- Морфинг меняет только `<path>`. Часть из `rect` или `circle` называется строкой «нарисуйте часть контуром `<path>`».
  Цель может быть любой фигурой.
- Цвета из `<style>` по классам живой SVG не читает. Морфинг видит только атрибуты и `style="…"` и смешивает такую
  фигуру как фигуру без своей заливки.
- lunasvg после каждой правки раскладывает документ заново, поэтому живыми делаются небольшие картинки (стенд: фигура
  0,17 мс на 256 px).
- Рамки из девяти частей и декораторы при смене ступени делаются заново целиком.
- В нодах «Логики» нет арифметики: «Плавность» от «Время мира» проходит морфинг за первую секунду мира. Растянуть его
  или запустить по событию можно в Luau.
