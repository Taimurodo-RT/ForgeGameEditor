# Архитектура ядра

Дата: 2026-10-03. Стек: C++20, SDL3 + SDL_GPU, flecs, Box2D v3, Luau, RmlUi, miniaudio (см. [stack-choice.md](stack-choice.md)).

Главное требование: **большие 2D-игры**. Маленькие игры тоже собираются, но архитектура рассчитана на большие миры, сотни тысяч объектов и десятки тысяч ассетов. Отсюда правило: всё, что растёт вместе с игрой, хранится плотными массивами, обрабатывается пакетами, параллельно и с подгрузкой по частям.

## 1. Целевые масштабы

Это ориентиры по умолчанию, их можно поменять. По ним ставятся стресс-тесты и бюджеты кадра.

| Что | Цель |
|---|---|
| Кадр | 60 FPS на среднем ПК (6 ядер, видеокарта уровня RTX 3060), 144 FPS на мощном |
| Размер мира | до 64 000 × 64 000 тайлов в одном мире, с подгрузкой по частям |
| Активные сущности | 200 000 с логикой и физикой в кадре |
| Статичные объекты и тайлы на экране | 1 000 000+ спрайтов за кадр |
| Частицы | 1 000 000+ на GPU |
| Проект | 50 000+ ассетов, редактор не тормозит при поиске и прокрутке |
| Загрузка | переход между зонами без экрана загрузки, сохранение и загрузка игры за секунды |

## 2. Слои ядра

```
Редактор          — шесть редакторов, документы, undo/redo, импорт
Модули            — жанровые шаблоны-пакеты: компоненты, системы, префабы, UI
Рантайм           — мир и стриминг, ECS, физика, рендер, звук, UI, скрипты
Данные            — рефлексия, сериализация, база ассетов, сборка (cooking)
Фундамент         — память, задачи (job system), контейнеры, математика, профилирование
Платформа         — SDL3: окно, ввод, файлы, потоки, GPU
```

Правило зависимостей: каждый слой знает только нижние. Рантайм не знает про редактор, поэтому экспорт игры — это рантайм без редактора, без лишнего кода.

## 3. Фундамент

- **Память.** Никаких new/delete в горячем коде. Покадровые линейные аллокаторы (сбрасываются каждый кадр), пулы для объектов одного размера, отдельные аллокаторы на поток. Учёт памяти по категориям (текстуры, звук, мир, скрипты) с бюджетами.
- **Ссылки через хэндлы.** Вместо указателей используются индекс и поколение (generational handle). Удалённый объект не превращается в висячий указатель, а данные можно переупаковывать.
- **Одна система задач.** Пул рабочих потоков с work stealing и графом зависимостей задач. flecs, физика, стриминг, сборка ассетов и рендер ставят задачи в этот общий пул, а не создают свои потоки. Box2D v3 и flecs умеют принимать внешний планировщик задач.
- **Профилирование с первого дня.** Tracy (зоны CPU и GPU, память, блокировки). Без замеров оптимизацию больших игр не сделать.
- **Без исключений и RTTI в рантайме.** Ошибки возвращаются значениями, проверки (assert) включены в отладочной сборке.

## 4. Данные

Это основа и для редактора, и для больших объёмов.

- **Рефлексия — единый источник правды.** Компонент описывается один раз: поля, типы, диапазоны, подписи. Из этого описания автоматически получаются инспектор в редакторе, сериализация, доступ из Luau и нод, сетевая и сохранённая версии. Реализация: метаданные flecs (flecs meta) плюс небольшой генератор кода из C++-описаний.
- **Стабильные идентификаторы.** У ассета есть GUID. У сущности в сцене есть свой стабильный ID, а не рантаймовый ID flecs: рантаймовые ID меняются между запусками, а ссылки в сохранениях и между сценами должны жить вечно.
- **Два формата данных.**
  - *Исходный (source)*: текст (JSON), по файлу на сцену-чанк или на объект, чтобы git и слияние работали на больших командах.
  - *Собранный (cooked)*: бинарные блоки, готовые к загрузке в память почти без разбора (memory-mapped, сжатие LZ4 или zstd). Игра грузит только cooked.
- **Конвейер ассетов.** Импорт → cooked-артефакт, кэш по хэшу содержимого, пересборка только изменённого, всё в фоне. Атласы текстур, сжатие (BC7), мип-уровни, нарезка звука делаются при сборке, а не при запуске игры.
- **База ассетов редактора.** SQLite: метаданные, теги, зависимости, миниатюры, поиск. Так проводник на 50 000 файлов отвечает мгновенно.
- **Версионирование схем.** Каждый формат несёт версию, есть миграции. Без этого проекты больших игр ломаются при обновлении конструктора.

## 5. Мир и большие объёмы

Здесь главное отличие от движков для маленьких игр.

- **Мир делится на чанки** (например, 64 × 64 тайла). Чанк — единица загрузки, выгрузки, сохранения и редактирования. Стриминг грузит и выгружает чанки по расстоянию до камеры и важных объектов в фоновых задачах.
- **Тайлы — не сущности.** Тайлмап хранится плотными массивами на чанк и слой (ID тайла, флаги, вариант). Один чанк-слой = один GPU-буфер, обновляется только изменённая часть. Миллион тайлов как сущности ECS убил бы и память, и время.
- **Статичный декор — тоже не сущности.** Деревья, камни, трава хранятся массивами экземпляров на чанк. Если игрок взаимодействует с объектом, тот на лету «повышается» до полноценной сущности.
- **Уровни детализации симуляции.**
  - *Активная зона*: полная логика, физика, анимация каждый тик.
  - *Ближняя зона*: упрощённая логика реже (например, раз в 4 тика), без физики.
  - *Спящая*: состояние сериализовано, время «догоняется» при возвращении (рост урожая, перемещение NPC по расписанию).
- **Координаты.** Позиция = номер чанка (целые) + локальная позиция (float). На больших расстояниях float теряет точность, такая схема снимает проблему. Рендер и физика работают относительно камеры или чанка.
- **Пространственный индекс** на чанк (сетка или хэш) для запросов «кто рядом»: ИИ, триггеры, «враги в радиусе 12 м» из нод.
- **Сохранения как разница.** В сохранение пишется только то, что отличается от cooked-мира: изменённые чанки и сущности. Сохранение большого мира остаётся маленьким и быстрым.

## 6. Симуляция

- **Фиксированный шаг** логики и физики (60 Гц по умолчанию) отдельно от частоты кадров, рендер интерполирует между шагами. Это даёт стабильную физику и воспроизводимость (повторы, отладка, будущий сетевой режим).
- **Фазы кадра** в строгом порядке: ввод → события → логика (скрипты) → физика → после физики → анимация → подготовка рендера. Модуль добавляет свои системы в нужную фазу.
- **Параллельность.** Системы flecs объявляют, какие компоненты читают и пишут, и планировщик запускает непересекающиеся параллельно. Каждая система внутри делит сущности на пакеты по потокам.
- **Физика.** Box2D v3: многопоточный, SIMD, спящие острова. Тела создаются и удаляются при стриминге чанков. Для простых случаев (тайловые коллизии, триггеры без физики) есть свой быстрый путь без Box2D.
- **События, а не опрос.** Логика реагирует на события («вошёл в зону», «здоровье < 0») через очереди событий, а не проверяет условия у каждой сущности каждый кадр.

## 7. Скрипты и ноды

- **Граф → промежуточное представление → Luau.** Граф нод хранится как данные. Компилятор превращает его в Luau-код. Высокоуровневые «человеческие» ноды — это шаблоны (макросы), которые разворачиваются в низкоуровневые. Отсюда «можно настроить подробно, но не обязательно».
- **Тяжёлое делает ядро, скрипт управляет.** Ноды вроде «Для каждого врага в радиусе» вызывают нативные системы, работающие пакетами, а не цикл на Luau по 10 000 объектам. Ноды пишут логику, ядро её исполняет.
- **Бюджеты.** Профилировщик показывает время каждого графа и каждой ноды. Дорогая нода видна прямо в редакторе.
- **Песочница и горячая перезагрузка.** Ошибка в скрипте не роняет игру и редактор. Изменённый граф перекомпилируется и подменяется на лету.
- **Отладка по нодам.** Карта «нода ↔ строка Luau»: точки останова и пошаговое выполнение показываются на графе.
- **Многопоточность.** Luau VM однопоточная. Скрипты работают в фазе логики. Независимые миры и зоны могут получить свои VM в разных потоках, если понадобится.

## 8. Рендер

- **Рендер — это извлечение данных.** ECS не рисует сама: фаза подготовки собирает из мира плотные массивы «что рисовать» (позиция, спрайт, слой, ключ сортировки), дальше рендер работает только с ними. Логика следующего кадра может идти параллельно с рендером текущего.
- **Пакетная отрисовка.** Инстансинг, атласы и массивы текстур, сортировка по ключу (слой, глубина по Y, материал) radix-сортировкой. Миллион спрайтов — это десятки вызовов отрисовки, а не миллион.
- **GPU-driven там, где объектов много.** Отсечение по экрану, частицы, сортировка больших слоёв — в compute-шейдерах.
- **Граф кадра (frame graph).** Кадр описан как проходы с входами и выходами: мир, свет, тени, частицы, постобработка, UI. Модули добавляют проходы (туман войны, вода, погода), не трогая ядро.
- **2D-свет.** Карты нормалей, буфер накопления света, мягкие тени через SDF препятствий в compute. Это то самое «серьёзное использование железа».
- **Стриминг текстур.** Бюджет видеопамяти, текстуры чанков загружаются и выгружаются вместе с миром, мипы в первую очередь.

## 9. UI

RmlUi для игры и редактора. Для больших игр важно: инвентари на тысячи предметов и длинные списки делаются виртуализированными (рисуются только видимые строки), привязка данных обновляет только изменённое, UI рисуется пакетами в общем рендере.

## 10. Редактор поверх ядра

- **Документная модель.** Редактор меняет исходные данные (документ) через команды. Команды дают undo/redo, а позже совместную работу. Мир рантайма в редакторе — это представление документа, которое синхронизируется разницами, а не перестраивается целиком.
- **Режим «Играть»** запускает копию мира в том же процессе, а после остановки мир возвращается к документу.
- **Большие проекты.** Редактирование по чанкам: открыт и загружен только видимый кусок мира. Все списки виртуализированы. Импорт и сборка ассетов идут в фоне и не блокируют работу.
- **Каждый редактор — модуль редактора** со своим документом, панелями и командами. Специализированные редакторы объектов (тайлмап, персонаж) подключаются так же, поэтому модуль-шаблон может принести свой редактор.

## 11. Шаблоны-модули

- **Модуль = пакет** с манифестом (имя, версия, зависимости) и содержимым: компоненты (схемы), системы (графы или Luau), префабы, UI-документы, ассеты, шаблоны редакторов.
- **Модули поверх модулей flecs**: подключение добавляет компоненты и системы, ядро не меняется.
- **Нативные модули** (C++ ради скорости) подключаются через стабильный C API ядра. Это путь для тяжёлых систем (например, симуляция жидкости или большая стратегия), а не для каждой мелочи.
- **Модуль редактируемый**: после добавления в проект его можно открыть и поменять в тех же редакторах. Так игра «собирается из шаблонов на ходу».

## 12. Как держать производительность

- **Стресс-сцены с первого месяца**: 200 000 сущностей, 1 000 000 тайлов, 1 000 000 частиц, проект на 50 000 ассетов.
- **Бюджеты кадра** по фазам (например, логика 4 мс, физика 3 мс, подготовка рендера 2 мс) и автоматические бенчмарки в CI: если коммит выходит за бюджет, это видно сразу.
- **Замер прежде оптимизации**: Tracy, счётчики GPU, отчёт по памяти.

## 13. Порядок разработки ядра

1. **Фундамент:** сборка, память, система задач, Tracy, логи, тесты.
2. **Данные:** рефлексия, сериализация source/cooked, база ассетов, сборка ассетов.
3. **Мир:** flecs, чанки, тайлмапы, стриминг, пространственный индекс. Сразу со стресс-тестом.
4. **Рендер:** SDL_GPU, пакетные спрайты, граф кадра, свет, частицы.
5. **Физика и симуляция:** фиксированный шаг, Box2D v3, события.
6. **Скрипты:** Luau, привязки через рефлексию, компилятор графа.
7. **UI и оболочка редактора:** RmlUi на SDL_GPU, документная модель, undo/redo, первый редактор (уровня).
8. **Вертикальный срез:** одна небольшая, но «большая по устройству» игра (мир из чанков, сохранения, диалог, UI) от начала до экспорта.

## Решения, которые зафиксированы этим документом

- Тайлы и статичный декор хранятся массивами на чанк, а не сущностями ECS.
- Мир делится на чанки, они же единица стриминга, сохранения и редактирования.
- Исходные данные в тексте для git, игра грузит только бинарные cooked-данные.
- Одна общая система задач на всё ядро.
- Рефлексия — единственный источник описания компонентов.
- Граф нод компилируется в Luau, тяжёлая работа — в нативных системах ядра.
