# Выбор стека для ядра 2D-конструктора

Дата: 2026-10-03. Ориентир: ПК (Windows/Linux/macOS), 2D, игры, которые всерьёз используют современное железо (много объектов, свет и тени, частицы на GPU, шейдеры, многопоточность). Конструктор должен быть простым для пользователя и подходить для любых жанров.

Это сравнение по общему знанию экосистем на осень 2026 года, без замеров. Цифры и оценки ниже относительные.

## Что требуется от основы

1. **Современный GPU API**: Vulkan / Direct3D 12 / Metal, compute-шейдеры, инстансинг, большие буферы. Это то, чего не хватало raylib (OpenGL 3.3, без compute и с ограничениями батчинга).
2. **Производительное и многопоточное ядро**: ECS с данными в плотных массивах, параллельные системы, многопоточная физика.
3. **Безопасный скриптинг для пользователя**: сам конструктор пишется на «тяжёлом» языке, а игры собираются из визуальной логики и простого скрипта, который не может уронить редактор.
4. **Редактор, который можно сделать быстро**: окна, инспектор, сцена, таймлайн, редактор тайлов.
5. **Контроль над ядром**: своё, а не чужой движок, чтобы архитектура жанров и плагинов была вашей.

## Кандидаты

| | C++20 + SDL3 | Rust + wgpu | C# (.NET) | Godot как основа | TypeScript + WebGPU |
|---|---|---|---|---|---|
| Современный GPU (compute, D3D12/Vulkan/Metal) | Да, SDL_GPU | Да, wgpu | Через обёртки (Silk.NET), меньше готового | Да, но через их рендерер | WebGPU есть, но с потолком браузера |
| Пиковая производительность | Максимальная | Максимальная | Высокая, есть паузы GC | Высокая для движка, но не ваша | Ниже всех, GC, однопоточность JS |
| Многопоточность | Полная | Полная и безопасная | Хорошая | Ограничена движком | Слабая (воркеры) |
| Скорость разработки ядра | Средняя | Ниже средней (компиляция, borrow checker) | Высокая | Очень высокая на старте | Высокая |
| Редактор | Dear ImGui, зрелый | egui, хороший | Avalonia, богатый UI | Готов, но это редактор Godot | HTML/CSS, самый простой |
| Зрелость библиотек для 2D | Максимальная | Хорошая, часть ещё меняется | Средняя | Готово | Средняя |
| Риск | Ошибки памяти | Высокий порог входа, смена API в экосистеме | Рендер-слой придётся собирать самому | Вы не владеете ядром, сложно сделать «свой» конструктор | Упор в производительность |

Коротко по каждому:

- **Godot как основа** быстро даёт результат, но вы делаете не конструктор, а надстройку над чужим движком. Это противоречит цели «сильное собственное ядро с самого начала».
- **TypeScript + WebGPU** даёт самый удобный редактор, но для «всерьёз нагружать железо» на ПК это потолок: GC, слабая многопоточность.
- **C#** отлично подходит для скорости разработки, но для 2D на D3D12/Vulkan придётся собирать рендер-слой почти с нуля, а готовые слои (Veldrid и т.п.) слабо поддерживаются.
- **Rust + wgpu** технически так же силён, как C++, и безопаснее. Минусы: медленная компиляция, высокий порог входа, часть экосистемы ещё меняет API. Хороший выбор, если вы уже уверенно пишете на Rust.
- **C++20 + SDL3** даёт самую зрелую экосистему, максимальную производительность и близкий к raylib стиль работы, но без его ограничений.

## Рекомендация: C++20 + SDL3

| Слой | Выбор | Почему |
|---|---|---|
| Язык ядра и редактора | **C++20** | Производительность, зрелые библиотеки, близко к опыту с raylib |
| Окно, ввод, геймпады, аудио-устройства | **SDL3** | Стандарт индустрии, отлично на ПК |
| Графика | **SDL_GPU** (часть SDL3) | Один API над Vulkan, D3D12 и Metal, есть compute-шейдеры. Шейдеры на HLSL, кросс-компиляция через SDL_shadercross |
| ECS | **flecs** | Быстрый, многопоточный, есть рефлексия, иерархии, запросы и модули. Модули удобно превращать в «жанровые плагины» |
| Физика | **Box2D v3** | Переписан в 2024 году под SIMD и многопоточность, держит десятки тысяч тел |
| Скрипты пользователя | **Luau** | Lua от Roblox: песочница, опциональная типизация, быстрый интерпретатор. Пользовательский код не уронит редактор |
| Визуальная логика | Своя, компилируется в Luau или в граф над ECS | Чтобы игры можно было собирать без кода |
| Редактор | **Dear ImGui (docking)** + ImNodes для графов | Самый быстрый путь к рабочему редактору |
| Текст | SDL3_ttf (FreeType + HarfBuzz) | Корректная кириллица и сложные шрифты |
| Звук | miniaudio | Микширование, эффекты, простое API |
| Сериализация | Рефлексия flecs, проекты в JSON (читаемо, удобно для git), сборка игры в бинарный пакет | |
| Сборка | CMake + vcpkg | Все библиотеки выше есть в vcpkg |

Если вы уже уверенно пишете на Rust, равноценная замена: Rust + wgpu + bevy_ecs (или flecs-rust) + egui + mlua (Luau). Архитектура ядра от этого не меняется, меняется только язык.

## Стратегия, чтобы ядро было сильным

1. **Ядро не знает про жанры.** Ядро даёт ECS, рендер, физику, ввод, ресурсы и скрипты. Платформер, RPG, стратегия, шутер — это модули (наборы компонентов, систем и шаблонов редактора) поверх ядра. Это и даёт гибкость по жанрам.
2. **Редактор и игра используют один и тот же рантайм.** Кнопка «Play» запускает ту же сцену в том же процессе, а экспорт игры — это рантайм без редактора.
3. **Рендер построен на пакетах и GPU с первого дня.** Спрайты рисуются инстансингом из больших буферов, частицы и 2D-свет считаются в compute-шейдерах. Именно это даёт «использование современного железа», которого не было в raylib.
4. **Всё данные, всё сериализуемо.** Любой компонент описан через рефлексию и сразу появляется в инспекторе, сохраняется в проект и доступен из скриптов. Без этого конструктор не станет простым.
5. **Пользовательская логика изолирована.** Luau и визуальные графы работают в песочнице, горячая перезагрузка скриптов и ассетов без перезапуска.
6. **Сначала вертикальный срез.** Одна простая игра от начала до экспорта, и только потом расширение. Детальная архитектура и дорожная карта — в следующих тредах.

# Уточнение после целей и дизайна (2026-10-03, вторая итерация)

Исходные данные: шесть редакторов (уровень, библиотека объектов, скрипты на нодах, сюжет, интерфейсы в духе Figma, библиотека ассетов), шаблоны-модули, дизайн-система Forge UI и макеты нодового редактора (анатомия нод, скрипты, диалоги, машина анимаций).

## Главное изменение: один UI-движок для редактора и для игр

Forge UI построена на «веб-эквивалентности»: слои фона, градиенты, тени и свечения, фильтры, трансформации, маски, переходы. Макеты нод используют то же самое: скругления, внутренние тени, ореол выделения, вариативный шрифт иконок. Dear ImGui так не рисует. Кроме того, редактор интерфейсов должен воспроизводить веб в игре, поэтому UI-движок в игре нужен в любом случае.

Решение: **RmlUi** (C++, MIT) вместо Dear ImGui как основа и редактора, и игрового UI.

- HTML/CSS-подобные документы (RML/RCSS): flexbox, переходы и анимации, а с версии 6 ещё box-shadow, градиенты, фильтры (blur, drop-shadow и т.д.), маски. Это почти один к одному модель Forge UI.
- Привязка данных (data binding), свои элементы на C++. Холст уровня, нодовый граф и холст Figma-редактора делаются как свои элементы.
- Редактор интерфейсов показывает игровой UI тем же движком, которым он будет работать в игре, поэтому что видно, то и получится.
- Редактор сам написан на этом UI. Это постоянная проверка движка: всё, чего не хватает редактору, не хватает и играм.

Что придётся сделать самим: рендер-интерфейс RmlUi поверх SDL_GPU со всеми эффектами (фильтры, маски, тени); текстовый движок на FreeType + HarfBuzz вместо стандартного (кириллица, лигатуры для иконок Material Symbols); CSS Grid в RmlUi нет, есть flexbox. Для Figma-подобной вёрстки (auto-layout) этого достаточно.

Dear ImGui остаётся только для внутренних отладочных панелей разработчика ядра.

## Остальное по редакторам

| Редактор | Что нужно от стека | Чем закрываем |
|---|---|---|
| Уровня | Тайлмапы, слои, свет, тысячи объектов | flecs + свой батч-рендер на SDL_GPU, Box2D v3. Без изменений |
| Библиотека объектов | Сущности из ассетов, общие и проектные, свои мини-редакторы | Префабы flecs, сериализация через рефлексию. Библиотека — пакет файлов на диске, общая лежит в папке пользователя, проектная — в проекте |
| Скрипты на нодах | Граф со вложенными блоками, абстрактные «человеческие» ноды, подробная настройка по желанию | Граф — данные, компилируется в Luau. Высокоуровневые ноды — это шаблоны, которые разворачиваются в низкоуровневые. Отладчик шагает по нодам через карту «нода ↔ строка Luau» |
| Сюжета | Диалоги и квесты с тестом без запуска игры; RPG-диалоги с вводом ключевых слов | Тот же нодовый редактор. Тест — это рантайм диалогов, запущенный прямо в окне редактора. Ввод ключевых слов: на старте словарь синонимов + стемминг (Snowball, есть русский) + нечёткое сравнение. Позже, по желанию, маленькая локальная модель эмбеддингов через ONNX Runtime для свободных фраз |
| Импорт Ren'Py | Полный перенос новеллы | Свой парсер языка сценариев Ren'Py: label, реплики, menu, jump/call, show/scene/hide, define, переменные. Python-блоки ($ и python:) переносятся, где понятно (присваивания, условия), остальное помечается для ручной проверки. Встроенный Python не нужен |
| Интерфейсов | Figma для игр, веб-возможности | RmlUi (см. выше), компоненты Forge UI как библиотека шаблонов |
| Ассетов | Проводник, редактирование, конвертация | Изображения: stb_image / libpng / libwebp, импорт Aseprite. Звук: декодеры miniaudio + libvorbis/libopus. Видео (если понадобится): FFmpeg под LGPL. Простое редактирование изображений — на GPU |

## Шаблоны-модули

Это влияет на ядро сильнее всего, и стек это поддерживает:

- Модуль = пакет: компоненты (описание данных), системы (графы или Luau), префабы, UI-документы, шаблоны редакторов. Всё это данные, поэтому модуль можно открыть и поправить в тех же редакторах.
- В основе — модули flecs: подключение модуля добавляет компоненты и системы без изменения ядра.
- Модули на C++ (ради скорости) возможны через стабильный C API ядра, но это исключение, а не основной путь.
- От «три в ряд» до большой RPG с видом сверху — разные наборы модулей поверх одного ядра.

## Итоговый стек (обновлённый)

C++20, SDL3 + SDL_GPU, flecs, Box2D v3, Luau, **RmlUi** (редактор и игры) + FreeType/HarfBuzz, miniaudio, CMake + vcpkg. Dear ImGui — только для отладки.

Альтернатива, которую стоит держать в уме: экосистема Rust/Linebender (wgpu + Vello для векторной графики на compute-шейдерах + Taffy для flexbox и grid + Parley для текста) ближе всего к «браузеру внутри движка», но в 2026 году она моложе и меняется быстрее. Если RmlUi упрётся в потолок, это главный запасной путь.
